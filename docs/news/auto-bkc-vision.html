Vision Roadmap October 14, 2026

Automatically selecting the best known configuration

Agentic coding has upended local AI software development in 2026. The number of important engines upstream of Lemonade is growing fast, and so is the number of important agents and apps downstream of it.

That gives Lemonade an exciting opportunity to serve as a central hub, similar to an "app store", where a curated selection of agents, engines, and models are distributed and "just work" with each other in a single click.

01Introduction

Why this matters

This work will improve adoption of local AI in both enthusiast and enterprise use cases by:

  • Improving purchaser confidence that systems will provide strong return on investment, based on upfront availability of data.
  • Lowering evaluation and deployment friction by automating the end-to-end journey for common out-of-box use cases.
02Vision

Pick an agent. Lemonade handles the rest.

The fragmented ecosystem of engines should be abstracted away from users and developers. They should be automatically presented with a "best known configuration" (BKC) for their use case, which we refer to as auto-BKC.

  1. Choose an agent

    The user selects an agent from a menu of options, such as Hermes, Pi, AnythingLLM, DeepSeek Harness, and more.

  2. Get a recommendation

    Lemonade recommends a default model and engine known to work well with that agent on that system. Users can select something different if they choose.

  3. Go live

    The entire stack of agent, model, and engine is automatically installed and configured. Live in minutes from 1 click.

Theory

Auto-BKC is possible because there are two subjective aspects to setting up a local AI agent, and everything else has an objective answer.

Subjective

What the user decides

  1. The agent itself, which must meet the user's unique use case.
  2. The model, since the results of every agent for every use case vary with model.

Deterministic

What Lemonade decides

  1. The best engine for the model, objectively selected from performance data for that system.
  2. Installing and configuring the engine to run the model on the target system.
  3. Installing and configuring the agent to talk to the engine and the user.

Note: we can recommend a default model for each agent and system combination based on benchmark data.

Note: future work may take this a step further by auto-optimizing the engine code itself for the specific hardware, model, and use case.

03Enabling technology

What we need to build

Four pieces of technology turn auto-BKC from an idea into a click: an engine database, a steady pipeline of engine integrations, an agent manager, and a smart router.

Engine database

Deterministically selecting an engine for a target system is possible when we have a comprehensive database of performance for all relevant model and engine combinations on that system.

Performance
Prompt processing (PP), token generation (TG), memory, and power, for both the single-user and batched cases.
Models
The latest releases from Qwen, Meta, Liquid, Google, and others.
Systems
Strix Halo first. Radeon 9700, Gorgon Halo, and non-AMD systems to follow based on availability.
Engines
Anything that has demonstrated significant community traction. At the time of writing that includes DwarfStar4, Halogen, Gufo, and strix-llama.cpp.

Correctness

Performance data for an incorrect implementation should be disregarded, so we'll adopt a way to assess whether an engine correctly implements a model. Donato's Terminal Bench Mini is a good candidate.

Official submissions

A baseline of data will be collected using AMD's DevLab cloud.

User submissions

User-submitted data extends coverage to more devices than DevLab has, emergent engines not already on our list, and engine parameterizations that are not part of our sweeps.

Engine integrations

New engines should be integrated into Lemonade as soon as they meet the following criteria:

  • Significant community traction.
  • Leadership in the performance database.
  • Clear differentiation from other engines, including non-performance differentiators such as software license, portability, and platform support.

Engines will be classified into three support tiers:

Core

Recommended for production use, with guaranteed support from industry.

Experimental

Supported long term by at least one trusted Lemonade maintainer.

Guest

Provided by an external party and deployed into a sandbox (e.g., containers, nono.sh). May be removed at any time.

Agent manager

The agent manager assists users with the installation, configuration, and launch of agents that work with local AI. It contains enough metadata about each agent's use case to enable auto-BKC, along with benchmark data, to recommend engines and models.

Candidate agents:

  • Pi
  • AnythingLLM
  • Hermes
  • DeepSeek Harness
  • Claude Code
  • Codex
  • GitHub CLI

We will also investigate deep integration of Pi into Lemonade, which could be used for:

  • Running agent skills, such as agentically optimizing the user's system.
  • Built-in quality benchmarking, by asking Pi to use an agent and model combination to complete a task and grading the result.
  • Serving the agent to downstream applications via an endpoint.

Note: we are still working to define this capability in more detail. It will have a phased rollout, first enabling easy-to-deploy, developer-first agents (e.g., Pi) before moving on to more complex cases. Model recommendations will be performed by humans until benchmark data is available.

Smart router

The smart router lets agents easily take advantage of on-prem token servers (e.g., Instinct Coder, Threadripper Halo) and cloud APIs when available. Our work will make these resources easier to configure, for example by integrating Lemonade Nexus.

04Maintainability

Scaling code velocity and quality together

As Lemonade grows, certain measures are needed to ensure that we can sustain both high code velocity and high quality.

Container strategy

Historically, Lemonade has preferred to distribute native engines. We're adopting containers as a distribution mechanism for two reasons:

  1. Enabling sandboxed deployment, which keeps users' systems and data safer than running native binaries as the lemonade user.
  2. Minimizing the amount of glue logic needed to integrate new engines and agents.

Once containerized backends are available, we will also investigate sandboxing native backends using nono.sh, and enabling container-based agents in the agent manager.

API contract

The Lemonade Contract is a set of CI tests that assert certain APIs never receive breaking changes. It solves two maintainability problems:

  1. PR reviewers need certainty that a PR they're approving won't have unintended downstream consequences.
  2. Downstream apps need certainty that they can take a dependency on these APIs.

Extensibility

Users should be able to try new agents, engines, models, and parameterizations without waiting for Lemonade to add in-tree support. Two extensibility interfaces make that possible:

  • Already-installed engines that meet a supported interface specification can connect to Lemonade's router.
  • Users can develop and distribute custom model catalogs, including model definitions that come with specialized parameterizations.

Planned refactors

A few major Lemonade code modules recently hit their maintainability limit: PRs became too difficult to review correctly, so we stopped accepting contributions to them. These refactors add specs, tests, and other guardrails that let agents autonomously write correct code, which will greatly increase code velocity.
