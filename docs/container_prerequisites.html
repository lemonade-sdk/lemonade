Container Prerequisites
What the toolbox backends need from your machine, and how to provide it

Why this page

Three Lemonade backends run inside OCI containers rather than as downloaded binaries: llamacpp-toolbox, ds4 and halogen. They are prebuilt images that bundle a complete ROCm or Vulkan stack, which is what makes them work on hardware where a plain binary would not.

Everything else about them is ordinary: Lemonade pulls, updates and removes the images for you, and you pick models from the model list as usual. The one thing Lemonade cannot install for you is the container runtime itself. If the backend manager shows one of these backends as action required, the section below matching its message tells you what to do.

No container runtime

Lemonade found neither podman nor docker on your PATH. Install one. Podman is preferred: it runs rootless by default, and it can pass your own group membership into the container, which removes the most common cause of GPU permission failures.

Podman Recommended

Install it from your distribution's repositories:

  • Ubuntu/Debian: sudo apt update && sudo apt install podman
  • Fedora/RHEL: sudo dnf install podman
  • Arch Linux: sudo pacman -S podman
  • openSUSE: sudo zypper install podman

Rootless podman needs no group changes and no daemon. Nothing else to do.

Docker

Follow Docker's install guide for your distribution, then add yourself to the docker group so you can reach the daemon without sudo:

sudo usermod -aG docker $USER

Log out and back in (or run newgrp docker) for the new group to take effect, then restart Lemonade Server.

Runtime installed but not usable

A container runtime is on your PATH, but it did not answer when Lemonade asked it for its version. Almost always this is a permissions problem with the Docker daemon socket, and it looks like this when you try it yourself:

permission denied while trying to connect to the Docker daemon socket

Add yourself to the docker group and start a new login session:

sudo usermod -aG docker $USER && newgrp docker

Then confirm it works and restart Lemonade Server so it re-probes:

docker version

If you would rather not grant daemon access, install podman instead and Lemonade will prefer it automatically.

User cannot open the GPU device nodes

The GPU is passed into the container through /dev/kfd and /dev/dri. Your user must be able to open them. Check your groups:

groups

If video and render are missing, add them and start a new login session:

sudo usermod -aG video,render $USER

A fresh terminal is not enough - group membership is picked up at login, so log out and back in, then restart Lemonade Server.

Rootless podman without keep-groups

Rootless podman maps your user into the container, but by default it does not carry your supplementary groups across, so the container ends up unable to open /dev/kfd even though you can. Lemonade passes --group-add keep-groups for you, which fixes this.

That option needs the crun OCI runtime; it is the default on current distributions but not on older ones. If a container fails with a permission error on the device nodes, check which runtime podman is using:

podman info --format '{{.Host.OCIRuntime.Name}}'

If it reports runc, install crun and make it the default:

sudo apt install crun # or: sudo dnf install crun

Then set runtime = "crun" under [engine] in ~/.config/containers/containers.conf.

/dev/kfd is missing

/dev/kfd is the AMD compute device node. Without it there is no GPU to pass into the container at all. Check whether the kernel driver is loaded:

lsmod | grep amdgpu && ls -l /dev/kfd

If amdgpu is not loaded, your kernel was built without it or the GPU is not supported by this kernel version. Update to a kernel that supports your GPU - for Strix Halo (gfx1151), see the kernel requirements page, which also covers the CWSR fix that every ROCm backend on that GPU needs.

/dev/dri is missing

The render node under /dev/dri is how the Vulkan toolbox variants reach the GPU. Check that it exists:

ls -l /dev/dri/

You should see at least one renderD* entry. If the directory is empty or absent, the graphics driver is not loaded; this is the same kernel-side problem as the section above.

Not enough GPU memory for large models

On Strix Halo the GPU shares system memory, and how much of it the GPU may use is set at boot. Out of the box the limit is roughly half your RAM, which is not enough for the largest toolbox models. Check the current limit:

cat /sys/module/ttm/parameters/pages_limit

That value is in 4 KiB pages, so multiply by 4096 for bytes. To raise it, add these kernel parameters to your bootloader configuration and reboot - the example allows about 96 GiB of GTT:

amdgpu.gttsize=98304 ttm.pages_limit=25165824

This is not a container requirement: it applies to any GPU backend on this hardware. Lemonade hides models it calculates cannot fit, so raising the limit also makes more of the model list visible.

Check the BIOS carve-out too

Many Strix Halo systems let the firmware reserve a fixed block of memory for the iGPU (a "UMA frame buffer" or "dedicated graphics memory" setting). That block is taken before the kernel boots, so it never shows up as missing: the machine simply reports itself smaller. Compare what the OS sees against what you installed:

grep MemTotal /proc/meminfo

A 128 GB machine reporting about 61 GB has roughly 64 GB carved out. For these backends that is usually the wrong trade: they reach the same unified memory through GTT whether the carve-out is large or small, and the reserved block comes straight out of the file cache that large mapped checkpoints read through. Setting the option back to Auto or its minimum (about 512 MiB) is what the Halogen authors recommend, and it costs the GPU nothing as long as GTT is sized as above.

Kernel too old for Halogen

The halogen backend needs Linux 7.0 or newer, which is ahead of what most distributions ship today. Check your kernel:

uname -r

If it is older than 7.0, there is no workaround: Halogen's memory path depends on kernel support that is not backported. Wait for your distribution to ship a 7.x kernel, or use one of the llamacpp-toolbox variants in the meantime - they run on the same GPU with no kernel floor beyond the CWSR fix.

Halogen also needs about 130 GB of free disk for its checkpoint bundle, and enough GPU memory to hold it. See the GTT section above.

Running Lemonade itself in a container

None of this works from inside Lemonade's own Docker image. The toolbox backends launch sibling containers, which a container cannot do without privileges that the Lemonade image deliberately does not request. Run Lemonade on the host to use them.
